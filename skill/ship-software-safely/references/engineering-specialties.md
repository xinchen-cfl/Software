# 软件工程专项原则

## 最小改动

- 每一行改动都应能用当前任务解释；
- 不把修复扩展成顺手重构；
- 两三处简单重复通常比提前抽象更便宜；
- 怀疑需要扩大范围时，先证明根因或依赖关系。

## 测试自动化

- 能用单元或接口测试证明的风险，不放进浏览器端到端测试；
- 端到端测试保留给跨组件关键用户路径；
- 等待可观察条件，不依赖固定睡眠时间；
- 测试拥有并隔离自己的数据；
- 波动测试必须定位根因，失败应留下足够诊断证据；
- 重试用于测量波动，不用于把红色结果刷成绿色。

## 秘密与凭据

- 秘密不得进入代码、Git 历史、日志、客户端产物或镜像层；
- 使用最小权限和尽可能短的生命周期；
- 每个凭据都应有负责人、轮换方式和撤销路径；
- 泄漏后应在提供方撤销或轮换；删除源代码中的值只是第一步；
- 报告泄漏位置和类型时不复述秘密原文。

## 数据库可靠性

- 没有验证过恢复的备份只是一份文件，不是恢复保证；
- 明确允许的数据损失和可接受恢复时间，再设计备份与恢复；
- 结构迁移检查锁表、兼容性、执行时长和应用回滚后的行为；
- 优先使用先扩展、后迁移、最后收缩的兼容演进方式；
- 应用产物回滚和数据恢复是两条不同路径。

## 生产可靠性

- 先建立与用户体验相关的可观察信号，再增加告警和自动化；
- 真实流量和风险需要时，再引入渐进式发布和服务等级目标；
- 事故处理优先明确影响、负责人、时间线、止损和恢复；
- 恢复路径应通过演练验证，不能只存在于文档中。

## 引入时机

这些能力按风险出现，不一次性全部建立：

```text
出现秘密或外部凭据 → 凭据生命周期
出现持久数据       → 备份、恢复和迁移策略
出现关键跨组件路径 → 最小端到端测试
出现真实用户流量   → 可观测性和可靠性目标
出现生产事故       → 事故响应和恢复演练
```
