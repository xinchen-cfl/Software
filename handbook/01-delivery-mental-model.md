# 从本地代码到生产：交付心智模型

## 1. 一条发布链究竟改变了什么

软件交付不是一个模糊的“上线”按钮，而是一组可以观察的状态变化：

```text
本地工作区产生改动
→ Git commit 保存代码快照
→ PR 把补丁带到共享分支
→ CI 在干净环境复现检查
→ 构建系统生成不可变运行产物
→ staging 运行并验证该产物
→ production 运行同一个产物
→ 必要时重新选择旧产物回滚
```

每一步都应该回答三个问题：

1. 输入状态是什么？
2. 这一步改变了什么？
3. 什么证据证明结果符合预期？

## 2. Git 中容易混淆的对象

### 工作区、工作树、分支和提交

- 工作区是你看到和编辑的文件。
- worktree 是一个受 Git 管理的独立检出目录。
- branch 是指向某个 commit 的可移动指针。
- commit 是不可变的代码快照，并通过 parent 形成历史链。

创建 branch 不会复制代码；创建 worktree 才会得到另一个目录。同一 branch 通常只在一个 worktree 中检出。

真正危险的不是“旧 branch”，而是：

```text
未提交 + 未推送 + 没人知道属于哪个状态的改动
```

只要工作已经 commit，它通常可以 rebase、cherry-pick 或恢复。

### 什么叫干净起点

干净不是“仓库里没有旧分支”，而是新任务所在工作树没有未知状态：没有未提交或未跟踪的未知文件，没有冲突或进行中的 Git 操作，当前提交对应已经确认的基础点，也不会覆盖其他任务。

基础点不一定永远是最新主分支。它应按用户指定、仓库规范、关联发布分支或依赖任务、远端默认分支的顺序选择，并记录明确提交编号。

继续一个开发中的旧任务时，工作树可以不为空，但已有修改必须归属明确。新任务遇到其他任务改动时，应使用独立工作树，而不是擅自暂存或删除。

### 获取与拉取

`git fetch` 更新本地对远端状态的认识，不修改当前检出的文件。`git pull` 在 fetch 后继续把远端历史整合进当前 branch。

因此，没有 pull 并不代表 Git 不知道远端发生了变化。

### 合并、压缩合并和变基

- merge 保留分支历史并增加 merge commit。
- squash 把整个 PR 的补丁压成目标分支上的一个新 commit。
- rebase 把提交重新建立在新 base 上，因此 commit SHA 会改变。

提交编号不同不一定代表代码不同。压缩合并或变基后，可用补丁比较或 `git cherry` 判断等价改动。

## 3. 测试不是一个统一动作

测试工具可以通用，测试内容必须针对项目编写。Python 项目可能使用 pytest，但 pytest 不会自动知道业务正确答案。

不同检查提供不同证据：

```text
针对性测试       检查当前行为
状态与差异       检查准备提交的实际范围
本地围栏         检查本机最终补丁
拉取请求持续集成 在干净统一环境复现
镜像构建         检查能否形成运行产物
预发布           检查产物在生产式环境的集成结果
生产             检查真实环境是否运行目标产物
```

如果代码、依赖、配置、生成文件和环境假设都没变化，立即重复同一个本地测试通常没有新增价值。跨越独立环境或状态边界时，即使执行相同测试，也可能产生新的证据。

## 4. 全局状态与并发

项目全局状态不是功能分支中的一份状态文件。真实状态分布在 Git、代码托管平台、持续集成、产物仓库和运行环境中。模型应在开始或恢复工作前、改变共享状态前按需聚合足够信息。

开发、测试和互不依赖的构建可以并发；对同一共享目标的冲突写入必须串行。例如两个任务不能无协调地覆盖同一个预发布环境，也不能同时部署或回滚生产。

证据与预期不一致时停止写入并重新取证，不能继续使用已经过期的全局视图。

## 5. 持续集成与持续交付

持续集成负责把检查自动化并留下共享证据，例如：

- 安装声明的依赖；
- 运行测试、lint、类型检查；
- 从合并后的 commit 构建镜像；
- 把产物保存到 registry。

持续交付负责改变运行环境，例如：

- 拉取指定镜像；
- 替换 staging 或 production 容器；
- 执行迁移和健康检查；
- 失败时回滚。

持续集成绿色不等于生产环境已更新。它只证明检查或构建阶段成功。

### 为什么本地测试后还运行持续集成

本地测试回答“当前电脑和工作区能否通过”；CI 回答“GitHub 上真正提交的代码能否在全新标准环境中通过”。CI 可以发现：

- 本地存在但未提交的文件；
- 虚拟环境中未声明的依赖；
- macOS 与 Linux 的文件名或平台差异；
- 本地缓存或环境变量造成的假通过；
- 与最新 base 合并后的问题。

如果 PR CI 可以被管理员绕过，那么合并后的构建流程保留一次最小测试很有价值：坏代码可以进入 main，但不应继续生成发布镜像。

## 6. 镜像、容器、标签与摘要

- 镜像是可重复启动的运行模板。
- 容器是镜像的一次运行实例。
- tag 是方便人识别的可移动标签。
- digest 是镜像内容的不可变指纹。

生产发布应该记录 digest：

```text
源代码提交 → 镜像摘要 → 运行中的容器
```

预发布和生产不应分别构建镜像。正确方式是构建一次，然后把预发布验证过的同一个摘要晋级到生产。

GitHub Actions 中的 `.dockerbuild` 构建记录也可能有自己的摘要；那是记录文件的指纹，不是容器镜像摘要。部署时应使用镜像仓库中的镜像摘要。

## 7. 预发布与生产

预发布是真实部署，但不承接真实用户流量。它应尽可能复现生产的运行方式，用来发现镜像启动、环境变量、依赖、网络、代理和架构问题。

生产是承接真实流量和数据的运行环境。

仅创建两个目录并不能形成隔离。隔离需要结合：

- 独立进程或容器；
- Compose project、网络和端口；
- 配置、Secret 和权限；
- 数据库和存储；
- 主机、集群或云账号；
- 入口与流量控制。

训练项目可以把 staging 与 production 放在同一服务器，但高风险业务通常需要更强隔离。

## 8. 回滚

应用回滚不是撤销 Git，也不是重新构建旧代码。它是让 production 重新运行一个已经存在、验证过的旧 artifact。

最小状态记录：

```text
当前产物
实际运行产物编号
上一个产物
回滚时撤下的产物
```

单级 `previous-image` 足够覆盖最基本回滚。需要回到更早版本时，再引入发布历史或 release ledger。

应用镜像回滚不自动等于数据库回滚。涉及 schema 和数据变化时，需要单独设计向前兼容迁移、备份和恢复策略。

## 9. GitHub 版本发布页不是发布列车

GitHub 版本发布页是可选的版本公告与下载页面，通常与 `v1.0.0` 标签、发行说明和安装包关联。

一个项目即使没有 GitHub Release，也可以通过 Actions、container registry 和部署系统完成真实生产发布。不要把以下概念混为一谈：

- 业务中的 `/release` 接口；
- 软件 release process；
- GitHub Releases 页面；
- GHCR Packages 中的运行镜像。
